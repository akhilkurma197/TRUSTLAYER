## Implemented

### Verdict evidence semantics

- `core/rules/risk_aggregator.js` no longer turns URL rule `PHISHING` alone into a confirmed phishing verdict. It returns `UNDER_REVIEW` with high risk and an explicit heuristic basis until page evidence supports a page-level conclusion.
- Model phishing predictions remain `UNDER_REVIEW` and are described as predictions, never verified observations.
- Only a completed full rendered inspection with a page assessment explicitly returning phishing can set `verifiedThreat`. Such a finding takes precedence over weak benign URL/model signals; conflicting model or URL evidence is returned in `conflicts`.
- Access-denied/content-unavailable results take an explicit inconclusive path. A 403 is not treated as phishing or successful target-page inspection.
- A completed assessment with no detected phishing indicators reports `NO_THREAT_OBSERVED`, not `SAFE`. Its summary explicitly says this does not prove the site safe or free of other threats. This is not a malware/scam/deceptive-download/copyright assessment.
- `core/evidence_report.js` builds a bounded, versioned case report. Reasons carry a kind and source, evidence references where available, and evidence timestamps/freshness. Missing/stale evidence is marked and cannot substantiate a verified threat. It separately labels phishing, malware, scams, deceptive downloads, and piracy/copyright concerns; unsupported categories remain `NOT_ASSESSED`.
- Authenticated, case-credential-protected `GET /api/cases/:id/evidence-report` exposes the report. It uses the existing operator and case-access authorization middleware.

### Interactive browser UI

- `investigation.html` adds explicit opt-in at Mode C case creation. Existing cases cannot be silently upgraded to interactive sessions.
- The panel shows session state, bounded recent events, action failures, and screenshot previews. It supports only existing navigate/click/type/screenshot APIs and cancellation.
- Calls use `trustLayerApiFetch`, existing same-origin session authentication, and the case-scoped HttpOnly cookie issued during case creation. The raw case token is not read into DOM state or placed in a URL.
- Existing API validators and supervisor controls remain authoritative. UI action controls are not a new browser execution path and do not expose a proxy or remote-debugging port.
- The URL-only home result now labels a no-indicator outcome `URL_ONLY_NO_INDICATORS`; it no longer displays “Verified Safe Web Link.”

## Remaining limitations

- This is an evidence-report foundation, not a malware scanner, reputation service, scam verifier, download analyzer, or copyright determination system.
- Redirect and URL rules are heuristic indicators. External direct-egress behavior remains unverified, as recorded in Phase 4.
- Evidence “freshness” is limited to timestamps relative to the investigation creation/report time; it does not cryptographically attest the source or prevent a compromised collector from fabricating observations.
- The report exposes a confidence value only when the model supplied one; no new calibrated confidence estimate is invented.
- Interactive browser workflow has passed the two Phase 4 Docker integration tests as operator-reported in `docs/phase-four-interactive-browser-audit.md`; this UI wiring has not been live-tested with Docker or browser automation in this phase.
- API report route authorization has a deterministic local regression test. No production deployment/browser CSRF or origin configuration test was run; existing API cookie/origin controls were preserved.
- Full Node and package suites were not run because existing test groups can resolve public hostnames, and this task prohibited public DNS/network use. Existing Phase 4 reported Docker counts were not rerun.

### Cookie assertion diagnosis - 2026-10-31

The Docker UI run stopped at the Playwright cookie assertion before starting the worker. The case-creation route sets the scoped cookie on its `201` response as `trustlayer_case_<caseId>` with `Path=/api; HttpOnly; SameSite=Strict; Max-Age=...`; it adds `Secure` only when `NODE_ENV=production`, and does not set a `Domain` attribute. In this opt-in test, the server is same-origin at `http://127.0.0.1:<ephemeral-port>` with `NODE_ENV=test`, so `Secure` does not block cookie acceptance. The UI calls the same-origin `/api/cases` route, and its API helper relies on browser cookies after operator session authentication.

The failure was in the test's lookup: `uiContext.cookies(base)` queried cookies applicable to the origin root `/`, while the case cookie's path is `/api`. Playwright filters cookies by the supplied URL path, so that query omitted a correctly scoped cookie. The test now queries `${base}/api/` and asserts the cookie's value without printing it, plus `HttpOnly`, path, `SameSite`, and the expected non-production HTTP `Secure=false` attribute. No application security behavior was changed. This diagnosis is based on the route's `Set-Cookie` construction and Playwright's URL-scoped cookie lookup semantics; the browser acceptance remains to be confirmed by the next authorized Docker run.

### Typing interaction HTTP 409 - 2026-10-31

The latest authorized Docker run reported HTTP 409 on the UI's bounded `type` action after roughly 138 seconds. The test's selector and payload match the local fixture (`#note`, bounded text) and the action schema accepted by the API/worker protocol; the failing test did not establish an invalid selector or protocol mismatch.

Code inspection confirms a lifecycle deadline regression. The supervisor originally set `sessionDeadline` at Docker container spawn, while the worker begins its interactive session only after Chromium startup, navigation, and initial inspection. The configured interactive allowance is 120 seconds. A slow startup could therefore consume the entire controller deadline before the worker was ready. A 409 is the controller's expected response when that deadline has elapsed. This matches the reported timing; the original run did not provide a worker event timestamp, so its exact startup duration is not independently measured.

The controller now leaves an interactive handle unready and without a deadline until it receives the worker's `navigation_completed` readiness event. It starts the bounded session allowance using the supervisor's receipt time, rejects actions before readiness, and does not publish the ready investigation result to the engine until the interactive-ready event arrives. Duplicate readiness events cannot extend the session. Missing readiness remains fail-closed. The Docker test now emits bounded diagnostics on non-200 typing responses: status, mapped safe error code, case/session states, recent event sequence/type pairs, action type, and worker readiness/exit/deadline/action-count fields. It does not print response bodies, page text, cookies, credentials, or tokens.
